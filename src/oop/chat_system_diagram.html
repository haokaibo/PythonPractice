3类图 — Class Diagram（服务层核心域模型）

从 Chat Service 的领域视角出发，覆盖消息、会话、群组、用户、在线状态、推送等核心实体及其关系。 实线菱形 = 聚合（aggregate）；虚线箭头 = 依赖；<<interface>> = 抽象契约。
User / Device Presence Conversation / Message Notification interface dependency
设计要点： ① Message.message_id 用 Snowflake 算法保证单调递增，客户端按 ID 排序即保证顺序； ② Message.idempotency_key 用于幂等去重（Redis Set 短期 + 数据库唯一索引兜底）； ③ Conversation.read_cursor 用"已读位点"代替逐条已读，多端同步时只传一个 msg_id； ④ INotificationChannel 抽象 APNs / FCM，便于扩展 WebPush 等新通道； ⑤ GroupConversation 继承 Conversation，通过 kind 区分 DM / GROUP； ⑥ fanOutToMembers() 是写扩散（≤100 人群组，写入放大 ×N，读取 O(1)）；若改为读扩散，则去掉此方法，listMessages() 内部实时查 membership，写入无放大但读取多一次查询——面试时主动提这个 trade-off 是加分项。

4网络拓扑图 — Network Topology（跨可用区部署）

展示跨两个可用区（AZ-A / AZ-B）的部署拓扑：客户端流量经 CDN + WAF → LB → 无状态服务实例（多副本）→ 数据层（Cosmos DB 主从、Redis 主从、Kafka 3 副本）。实线 = 主流量，虚线 = 复制/故障转移。
连接层 / Redis 消息链路 / Cosmos / Kafka Presence 通知 / 外部推送 跨 AZ 复制 AZ-A 边界 AZ-B 边界
高可用要点： ① 所有无状态服务（ConnGW / Chat / Presence / Notif）在两个 AZ 各部署 ≥2 副本，LB 健康检查剔除故障实例； ② Cosmos DB 主从跨 AZ 异步复制，单 AZ 故障时读流量自动切到副本 AZ； ③ Redis 主从跨 AZ，连接路由表故障时 ConnGW 用本地 LRU 兜底 + 重建； ④ Kafka RF=3 跨 AZ，min.insync=2 保证单 AZ 故障不丢消息； ⑤ 可引入 chaos engineering：随机 kill 一个 ConnGW 实例，验证 WS 客户端自动重连到另一 AZ。
